## 4. What to build

**In plain words.** Every stake has its own secret device key. The stake sends it on every upload in the `Authorization: Bearer <device key>` header. The server stores only an argon2 hash of each key (`devices.key_hash`), never the key itself.

This card builds the check that `POST /api/readings` will run as step 1 of spec 10.1. The endpoint itself is B3's job; B3 calls this check.

**1. The shared error helper, in `server/app/errors.py`.** This card is the first to need the one error shape in spec 10.6, so it creates the helper. Later cards (B3, B6 and on) reuse it.

- `ApiError`: an exception that carries an HTTP status, a `code` and a `message`.
- A function that turns an `ApiError` into the 10.6 body: `{ "error": { "code": ..., "message": ... } }`.
- In `server/app/main.py`, register one FastAPI exception handler that turns any `ApiError` into a JSON reply with its status and the 10.6 body. Add no routes.

**2. The key check, in `server/app/device_auth.py`:**

```python
def authenticate_device(session, serial, authorization_header) -> Device
```

It returns the stake's `devices` row when the key is right. Otherwise it raises `ApiError` with status 401:

1. The `Authorization` header is missing or isn't `Bearer <something>`: 401.
2. No stake has this `serial`: 401.
3. The key doesn't match `devices.key_hash`, checked with argon2-cffi's `PasswordHasher().verify`: 401.
4. A **retired** stake with the right key is **not** rejected: it's returned like any other, and later gets the paused config (spec 8.5.1).
5. Every 401 has the same `code` and `message`, so the reply never says which part failed (unknown serial, missing key or wrong key).

**3. A helper for making keys**, in the same file: `hash_device_key(key) -> str`, the argon2 hash stored in `devices.key_hash`. B17's `create_device` uses it, so keys are always made and checked the same way.

#### Spec 8.7 Security baseline

- HTTPS for everything over the network. No reusable credential in plain text.
- Each stake has its own random device key, sent as Authorization: Bearer, never committed to the repository, and stored on the server only as a hash (DEC-18). A leaked key is replaced by re-provisioning over USB.
- Every stake upload is authenticated and checked against the schema.
- Dashboard actions need a logged-in user. Writes need Content-Type: application/json, except the photo upload.
- Photo uploads: JPEG or PNG only, under 5 MB, checked before any vision API call.
- The pump's runtime, daily and interval limits are enforced in firmware, so they hold even if the server is compromised.
- Credentials stay out of the repository and out of demo screenshots.

From spec 10.1:

1. Look up the stake by serial. Unknown serial, or a key not matching key\_hash → 401. A retired stake is not rejected: it continues below and receives the paused config in 10.2.

From spec 8.5:

**Two codes, two jobs.** The device key is the stake's ID badge: in the firmware, never typed by a person, proving a real stake is talking. The claim code is the sticker: proving you physically hold the stake, typed once, then dead.

From spec 8.5.1:

- A retired stake authenticates and syncs normally. Its config reply carries null dry\_raw and wet\_raw and status "attention" (10.2). Null calibration already means the stake will not water (7.2), so the stake pauses with no firmware change. It keeps taking readings and buffering them.

From spec 9.2 (the table definitions):

```sql
CREATE TABLE devices (
  id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY,
  serial VARCHAR(32) NOT NULL UNIQUE,
  key_hash VARCHAR(255) NOT NULL,                      -- argon2 hash of the device key
  claim_code_hash VARCHAR(255) NULL,                   -- NULL once burned
  claimed_at DATETIME(3) NULL,
  account_id BIGINT UNSIGNED NULL,
  plant_id BIGINT UNSIGNED NULL UNIQUE,
  name VARCHAR(100) NULL,
  ml_per_s DECIMAL(5,2) NULL,                          -- measured at G11
  firmware_version VARCHAR(32) NULL,
  last_seen DATETIME(3) NULL,
  retired_at DATETIME(3) NULL,                         -- set while retired (a pause, 8.5.1); NULL = active
  FOREIGN KEY (account_id) REFERENCES accounts(id),
  FOREIGN KEY (plant_id) REFERENCES plants(id)
);
```

The spec doesn't answer these. Don't invent an answer: ask in the pull request (owner: Eli).
